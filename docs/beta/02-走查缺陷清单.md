## 二、修复详情与验证

### P0-1 · 「参与」被误判为「已有」

**现象**：只参与过接口开发的同学，被判定为「已有项目经验」，给出「再做一个项目」这类空话建议。

**根因**：GAP_SYSTEM 的三分类判定只区分「有没有线索」和「够不够」，**没有区分用户在项目里的角色深度**。

**修复**：在 `server/prompts.js` GAP_SYSTEM 新增三条规则：
- 规则 13 —— JD 出现「独立负责 / 主导 / 负责…模块 / 从 0 到 1」这类角色深度词时，
  只参与过的经历判 improve，并要求 advice 指向「补上独立负责的证据」
- 规则 13b —— 「我们组拿了奖」只能证明团队有该成果，不能证明个人具备；
  除非原文明说「我主导」或明确是个人赛
- 规则 14 —— 不得因为「项目存在」就默认用户具备该项目所需的全部能力

**修复前后对比（sim-09 参与非负责人型）**：

| | 改前 | 改后 |
|---|---|---|
| 三分类 | have 0 / improve 0 / unknown 12 | **have 0 / improve 5 / unknown 10** |
| 「功能设计与迭代」判定 | 信息不足 | **待提升** |
| 对应建议 | — | 「把报名功能从需求梳理、接口设计到联调上线**完整走一遍**，输出一份功能设计说明」 |

关键变化：建议从「再做一个项目」变成「把**已有**的那个项目独立做完整」——
这正是知涯想要的「指出具体缺口」，而不是泛泛而谈。

### P0-2 · 非技术背景用户拿到技术类错配建议

**现象**：汉语言文学专业投内容/用户方向，建议里出现「学 Java / 掌握 MySQL」。

**根因**：计划生成只看「差距项 → 任务」的映射，没有考虑用户当前起点，
输出了岗位通用最优路径而非用户可达路径。

**修复**：在 `server/prompts.js` PLAN_SYSTEM 新增两条规则：
- 规则 8 —— 背景可行性：任务必须建立在用户已具备的东西上；
  非技术背景投内容岗不得出现技术任务；优先给「用 A 补 B」的任务；
  确实需要技术的差距先给零门槛替代动作铺垫
- 规则 9 —— 两周可达：任务之间要能串起来，后一条最好能用上前一条的产出

**修复前后对比（sim-05 纯文科型）**：

| | 改前 | 改后 |
|---|---|---|
| 三分类 | have 0 / improve 1 / unknown 6 | **have 1 / improve 0 / unknown 6** |
| 技术类错配任务 | 有 | **0 条** |
| 任务链路 | 建议去学技术 | 拆解运营规律 → 用户访谈 → 编码痛点 → 写投递说明 → 反推选题 → 改写发布 → 竞品对比 |

改后正确识别出「看过小红书运营账号」是相关经验（have 从 0 变 1），
且 7 个任务形成完整作品链路 —— 一个文科生两周后能拿出
「3 篇笔记 + 1 份访谈记录 + 1 份痛点清单 + 1 页投递说明」。

### P1-3 · 岗位方向为空时的两种空态

**现象**：部分请求返回 `directions: 0`，前端只显示「没能给出可靠的方向建议」，
用户不知道是网络问题还是自己信息不足。

**根因**：`runDirections` 的 catch 静默吞异常返回空数组，
「模型没给出」与「调用失败」被混为一谈。

**修复**：
- `server/pipeline.js` 新增 `runDirectionsWithStatus`，返回 `{ list, failed }`
- `server/index.js` 把 `directions_failed` 透出到 `meta`
- `public/app.js` 按状态给不同文案：
  - 调用失败 → 「方向建议这次没生成出来（网络或模型服务波动）。能力差距分析与行动计划不受影响」
  - 信息不足 → 「建议补充更具体的经历后重试」

### P1-4 · 等待期无进度语义、无重试提示

**现象**：分析耗时 18–95 秒（网络抖动时模型重试 2 次，耗时接近 3 倍），
但加载页文案固定，用户以为卡死。

**根因**：后端有 `retryState`，但只在**响应结束后**才随结果返回，
等待期间前端无从得知。

**修复**：
- `server/cloud.js` 新增请求级进度追踪 `beginProgress / updateProgress / getProgress / endProgress`，
  **按 requestId 隔离**（原来的 `retryState` 是全局单例，并发请求会互相覆盖，
  导致 A 请求读到 B 的重试次数）
- `server/pipeline.js` 在每步开始前上报步骤名
- `server/index.js` 新增 `GET /api/progress?requestId=xxx`
- `public/app.js` 轮询该接口（1.5 秒一次）：
  - 实时点亮对应的步骤（用户知道跑到第几步）
  - 重试时显示「网络不稳，正在自动重试（第 N 次）…请不要关闭」

**实测进度轨迹**（真实请求采样）：

```
正在解析你的经历    | retry=false | 等待 1s
正在拆解岗位要求    | retry=false | 等待 4s
正在逐条对照能力差距 | retry=false | 等待 8s
正在生成两周行动计划 | retry=false | 等待 13s
```

### P2-5 · 离线单文件版与线上不一致

**现象**：仓库里的 `demo-offline.html` 停留在旧版本，不含内测模式，
与线上行为不一致 —— 面试官从 GitHub 拿到的离线版和实际看到的不一样。

**根因**：`build/single-file.js` 只写桌面版，仓库那份是早期手工复制的，此后一直不同步。

**修复**：构建脚本同时写回仓库 `demo-offline.html`，并打印同步路径。
构建后两处 MD5 一致（`d5abae27...`），体积 82.7 KB。

### P2-6 · 离线版「填入示例内容」后按钮仍不可点

**现象**：离线版点「填入示例内容」后，「继续」按钮看起来能点，实际点不动。

**根因**：`fillDemoInputs` 只 `classList.remove('dis')`，
**没有解除 `disabled` 属性** —— 样式上不禁用，但行为上禁用。

**修复**：同时设置 `btn.disabled = false`。
全局检查确认其余 `dis` 类与 `disabled` 属性均已成对处理。

**附带修复**：离线版（`file://` 协议）下埋点请求会打向 `file:///C:/api/telemetry`，
控制台刷一片 `net::ERR_CONNECTION_REFUSED`。现在离线版直接跳过埋点与反馈上报，
演示时控制台干净。

## 三、修复过程中新发现的问题

修复 P2-6 时发现一个**此前从未被测到的回归**：
`fillDemoInputs` 的 bug 是之前把按钮从 `div` 改成 `button`、
加入真正的 `disabled` 禁用逻辑时引入的。
这类问题只有真正把离线版点一遍才会暴露 —— **这也是为什么离线版必须重新构建并实测**。

## 六、怎么把这份清单讲给面试官

这不是缺陷列表，是**产品迭代证据**。标准讲法：

> 「V1 上线后我用 12 组受控输入做了一轮系统走查，覆盖信息不足、矛盾 JD、非技术背景、
> 参与非负责人、转专业这些边界情况。走查暴露了 6 个问题，其中 2 个影响结论可信度 ——
> 比如模型会把『参与过接口开发』判成『已有项目经验』，这对求职建议是误导。
>
> 我判断根因在提示词缺少『角色深度』维度，加了三条判定规则后重跑：
> 该案例的三分类从『全判信息不足』变成『5 条精准判为待提升』，
> 建议也从『再做一个项目』变成『把已有项目独立做完整』。
>
> 另外还修了等待期无进度反馈的问题 —— 加了请求级进度追踪，
> 用户现在能看到『正在生成两周行动计划，已等待 13 秒』，
> 网络抖动时也会明确告知正在重试。」

关键在于：**你展示的是「发现问题 → 判断优先级 → 定位根因 → 修复 → 量化验证」这个闭环**，
而不是「我做了个东西」。前者是产品经理，后者是执行者。
