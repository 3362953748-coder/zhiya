# 第二部分：给组织者（你）的执行清单

## A. 准备工作（30 分钟）

- [ ] **确认线上服务正常**：打开 https://zhiya-career-41390.app.workbuddy.host/?sharecode=ZIDF2K3Q6W ，跑一次完整流程，确认能出结果
- [ ] **重置采集数据**：确认 `data/events.jsonl` 是空的（正式内测从零开始）
      ```bash
      rm -f data/events.jsonl data/feedback.jsonl
      ```
- [ ] **准备四份 JD**：给四个方向各准备一份**真实**的岗位 JD，让同学照着填。方向不同，测试才有对比价值：
      - 软件测试：测试开发实习生 JD
      - 软件开发：后端/全栈开发实习生 JD
      - 产品经理：AI 产品经理实习生 JD
      - 后端开发：后端开发工程师实习生 JD
      > 现成素材见同目录《04-内测JD测试素材.md》（16 份 JD，含完整/极简/矛盾三种版本，
      > 每份改写自真实 JD 原文并标注来源）；岗位依据见《05-岗位JD调研报告.md》（75 条来源链接）
- [ ] **准备编号分配表**：给同学分配编号（如 cq-01 ~ cq-15），避免撞号。用一个表格记：编号 / 姓名 / 方向 / 是否完成。**姓名只在你自己的表里，不进产品**

### 关于「真人测试」和「代演走查」的区别（重要）

这套工具支持两种数据来源，**报告会自动区分并如实标注**：

| | 真人内测 | 代演走查（`scripts/simulate-walkthrough.mjs`） |
|---|---|---|
| 谁在操作 | 你的同学 | 预设剧本 |
| 经历/JD | 同学自己填 | 预设文本 |
| 问卷回答 | 同学自己答 | 预设答案 |
| **模型调用** | **真实** | **真实** |
| **服务端校验** | **真实** | **真实** |
| **UI 流程** | **真实** | **真实** |
| 满意度等主观指标 | **有效** | **无效**（仅验证链路通畅） |
| 适合的用途 | 证明"有人真在用" | 快速覆盖边界情况、回归验证 |

**代演走查的价值**：它能用 12 个受控输入覆盖「信息不足 / 矛盾 JD / 非技术背景 / 参与非负责人 / 转专业」这些边界情况，真实用户短期内很难凑齐这些样本。它发现问题很快。

**代演走查的局限**：**绝不能对面试官说成是真人用户数据**。报告顶部会自动写明「研究者代演」，主观反馈一节也会打上警示标注。

**建议路径**：先跑代演走查（10 分钟出结果、修 bug），再用真人内测覆盖主观指标。真实用户数据一到，直接重跑报告生成器即可自动替换。

## B. 找人（关键，别跳过）

**推荐话术**（私聊，比群发有效）：

> 学妹/学弟～我在做 AI 产品，内测需要 10 分钟，你看这个工具对你求职有用吗？
> 有真实 JD 分析 + 差距诊断，测完填个 30 秒反馈就行。
> [链接]

**优先找这四类人**（每类至少 3 人，才能看出方向差异）：
- 想做**软件测试**的（通常关注"我差什么才能投测试"）
- 想做**开发**的
- 想做**产品经理**的
- 想做**后端**的
- 加上 1-2 个**明确说自己不想做技术**的（汉语言、法学、设计等），用来检验产品对非技术用户是否友好 —— 这一档最容易暴露问题

**目标**：10-15 人，其中至少 8 人完成完整分析。

## C. 现场监督（提高完成率的关键）

同学自己测最容易卡在"不知道经历怎么写"。建议：

- [ ] **组织一次 20 分钟的集中测试**（教室/自习室/线上会议都行）：你现场演示一遍，大家跟着做
- [ ] 或：**你先用 3 分钟录一段屏幕操作视频**发群里，降低他们的上手成本
- [ ] 准备好一段**示例经历**（可直接粘贴的那种），发给卡住的同学：
      > 我是软件工程专业大三学生，做过校园二手交易平台的课程项目，负责后端接口和数据库设计，还参加了程序设计竞赛拿过校级二等奖，没有实习经历。

## D. 数据采集与报告

**采集是自动的** —— 同学填了编号之后，漏斗事件和分析摘要会自动写进 `data/events.jsonl`。

跑完内测后生成报告：

```bash
node scripts/beta-report.mjs --md 内测报告.md
```

报告会告诉你：
- 参与人数、完成分析人数、漏斗每一跳的转化率
- 平均耗时、任务可判定率、时长不超预算率、零违规率
- 按求职方向的人数分布
- 问卷的有用度分布、推荐意愿、**参与者的原话**
- 以及**数据边界说明**（样本代表性、不做因果推断等）

**给面试官看时，用这份自动生成的报告，不要手写数字。**

## E. 需要重点盯的 4 个风险点

| 风险 | 怎么发现 | 怎么处理 |
|---|---|---|
| **样本量太小**（<5 人） | 报告"数据局限"节会自动提示 | 补人再跑，或在报告里如实写明样本量。**不要把 3 人的数据说成"用户测试"** |
| **同学随便乱填**（比如全填"张三"或"123"） | 看 `data/events.jsonl` 里 participant 是否高度重复 | 发现后剔除该条数据，在报告里说明剔除原因 |
| **演示模式混入** | 前端演示模式不计入 `analysis_done` | 已有防护，但要检查同学是否误开了演示模式 |
| **时间集中在一小时内** | 报告"数据采集区间" | 真实内测就是集中的，这在报告里如实呈现即可，不要声称"持续多日观察" |

## F. 给下一版攒需求

内测结束当天，把这三样整理成一页纸（这是产品经理的日常产出，也是面试时能讲的东西）：

1. **问题清单**：按「反馈提及次数」排序，每条写清楚「谁说的 → 原话 → 我的判断（是真问题还是预期外使用）→ 改不改 → 什么时候改」
2. **改版前后对比**：改了哪几处 → 重新跑内测 → 数据变化（如完成率从 X% 到 Y%）
3. **决策记录**：砍掉了什么、为什么砍（这类内容在 AI PM 面试里比功能清单值钱得多）
