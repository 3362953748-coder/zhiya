## 修了什么

### D1「待提升」分类从不出现（高，5/5 命中）

**根因不是代码 bug，是 PRD 规则空白 + 提示词自相矛盾。**

- PRD R-3「用户未提供的信息一律归为信息不足，禁止判定为不具备」—— **这条完全正确**，它管的是「完全没提」
- 但 PRD 里**没有任何一条规则定义「待提升」怎么判定**
- `prompts.js` 把 improve 也定义成「找不到任何对应线索」，等于把待提升这一栏从定义上抹掉

**修法**：重划三分类边界 + 写入三步判定顺序（找线索 → 判够不够 → 给动作），并新增纪律「improve 必须同时给 advice 和 prompt」。

### D2 假阳性判定（严重，2/5 命中）

**V1.0 报告的根因判断不够深。真凶是 `applyBasisConsistency`——服务端自己在造假证据。**

模型其实正确判了 unknown，依据写的是「但**未说明**是否使用 Excel 做过数据统计…按规则判为信息不足」，然后服务端的逻辑冲突检测规则：
1. ADMIT 正则命中的是前半句的「岗位要求…具备」（说的是 JD，不是用户）
2. DENY 正则漏了「未说明」
3. 把证据填成字符串「依据中已明确说明」——**那不是用户说的话**

**修法**：拆分依据只取用户段 / 补齐否定词 / 改判必须有真实原文 / 拦截元话语 / 名实分离防护 / 工具挂靠校验 / 语义相关度校验（共 7 处）。

### 额外挖出 3 个（V1.0 报告未列）

1. **JD 名实分离** —— 模型把「熟悉 MySQL」标成「大模型API」，item 被改名、evidence 却没改
2. **工具技能误挂** —— 规则不检查「这个工具是否属于这项能力」
3. **竞赛判定抖动** —— 同一输入在 have/improve 间随机跳

**修一个缺陷，挖出三个。** 这三个串在同一条链上，共享一个根因：服务端在「帮助模型」的时候，把不该帮的地方也帮了。

### 顺带消失 3 个（没为它们写一行代码）

D3（信息不足占比过高）、D4（任务拆碎）、D5（翻资料型元任务）——**根因都在 D1**。

一个根因修正，三类用户可感知的体验问题同时消失。**不修 D1 而单独修 D3/D4/D5，等于在症状层面打补丁。**

## 这次修复暴露的方法论问题（面试可讲）

### ① 自动化测试全绿 ≠ 产品是对的

V1.0 时 225 项测试全通过，产品却有两个 P0。**因为测试用例围绕「预期输入」设计，而两个 P0 都发生在「模型输出不合预期」的路径上。**

测试要覆盖「模型可能犯的错」，而不只是「我想要的输出」。

### ② 修复不能只看指标变好

T1 的「逻辑思考能力」修复后从 have 变成 improve，have 总数没变——**但判定是更准的**（V1.0 的证据「竞赛 + 刷题」确实不足以支撑「逻辑思考与问题排查」）。

只看「improve 从 0 变成 12」就宣布成功，会掩盖 T4 的 unknown 从 8 降到 2 这种实质体验改善。

### ③ 新增测试必须带对照组

修 D2 时一度把「视觉设计能力」误伤（概括能力名与具体工具名本就无词元重叠），**对照组立刻把它抓了出来**。

只测修复用例、不测对照组，会把过修复当成修复。

## 现在的作品集叙事链

```
用户研究（4 人深访，5 条洞察）
  → 竞品分析（5 款，功能矩阵 16 维）
     → 产品决策（三个核心问题，证据可追溯）
        → PRD（50 条验收标准）
           → 可运行 MVP（1.1 万行，225 项测试）
              → 代理走查（5 个专业，7 类缺陷）
                 → 修复 + 回归（149 项单测，225/225 产品测试）
                    → 复测确认（improve 0→12，假阳性 2→0）
```

**每一环都有产物、每一环都有数字。** 这就是产品岗面试想听的东西。
