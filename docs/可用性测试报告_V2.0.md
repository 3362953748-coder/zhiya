## 一、修复了什么

### 1.1 D1｜「待提升」分类从不出现（已修复）

**根因**：`server/prompts.js` 第 102 行对 improve 的定义是「岗位明确要求这项能力，但经历档案里**找不到任何对应线索**」，而第 106 行的绝对规则第 1 条要求「找不到任何对应线索 → status 必须是 unknown」。两条规则直接冲突，模型只能服从更具体的规则 1，把所有情况倒向 unknown。

**这个冲突的本质**：PRD R-3 规定「用户未提供的信息一律归为信息不足，禁止判定为不具备」——**R-3 本身完全正确**，它管的是"完全没提"。但 PRD 里**没有任何一条规则定义「待提升」怎么判定**，这是规则空白。而 prompts.js 把 improve 也定义成了"找不到线索"，等于把待提升这一栏从定义上抹掉了。

**修法**：给三分类重划边界，并写入判定顺序。

| 状态 | 修后定义 | 判定依据 |
| --- | --- | --- |
| have（已有） | 有明确证据，能说清用户做过什么 | 证据可回指且语义支撑该项能力 |
| improve（待提升） | **有相关线索但深度不够** | 用户做过相邻的事，但强度/规模/完整度达不到岗位要求 |
| unknown（信息不足） | 完全找不到相关线索 | 用户压根没提，无法判断 |

提示词里新增「判定顺序（必须按此顺序走完三步）」：先找线索 → 无线索则 unknown → 有线索则判够不够 → 够则 have、不够则 improve → 最后给具体动作。

**同时新增的产品纪律**：improve 必须同时给 advice（具体提升动作）和 prompt（一个能确认深度的追问）。这让"待提升"从一句标签变成一个可执行的下一步。

**修复效果**：improve 从 0 条变为 12 条，且每条都带具体建议。例如：

| 被测者 | 能力项 | 修复前 | 修复后（待提升 + 具体建议） |
| --- | --- | --- | --- |
| T4 产品 | 原型工具使用 | 信息不足 | 用 processon 完整画一份学生会报名排班小程序的页面流程图和低保真原型，并请一位产品方向的前辈给出修改意见 |
| T2 运营 | 数据跟踪与迭代优化 | 信息不足 | 针对自己运营过的公众号或小红书内容，做一次数据复盘表：记录每篇的阅读量、点赞、发布时间，并据此调整下一篇的选题和标题 |
| T1 技术 | 逻辑思考能力 | 已有 | 在课程项目中挑一次真实遇到的 bug 或接口异常，记录从定位到解决的过程，形成一段可讲述的排查案例 |

注意 T1 那一行：**修复后反而从「已有」变成了「待提升」**——因为 V1.0 时它虽然判成 have，但证据其实是"竞赛获奖 + 刷 LeetCode 200 道"，与"逻辑思考与问题排查能力"确实有距离。**修复让判定更准确，而不只是让数字更好看。**

### 1.2 D2｜假阳性判定（已修复，根因比 V1.0 报告所述更深）

V1.0 报告把根因归为「`isEvidenceTraceable` 只做子串匹配，不判语义相关性」。**实际排查后发现，真凶是 `applyBasisConsistency`——服务端自己的代码在造假证据。**

**真实链路**（T5「数据跟踪与迭代优化」案例）：

模型实际上正确判了 unknown，依据写的是：
> 「岗位要求熟练使用 Excel 等办公软件并具备基础数据处理能力…；经历档案中提到整理简历、跟进入职流程，**但未说明**是否使用 Excel 做过数据统计或档案维护，也没有可回指的证据片段，按规则判为信息不足。」

然后 `applyBasisConsistency` 这条"修复模型自相矛盾"的规则把它改判成了 have，原因有三：

1. **ADMIT 正则命中的是"岗位要求…具备"** —— 那说的是 JD 的要求，不是用户的能力。一句依据里同时描述岗位要求与用户实况，光看关键词分不清在说谁
2. **DENY 正则漏了「未说明」**（只覆盖了「没有说明」）
3. **改判时把证据填成字符串「依据中已明确说明」** —— 那不是用户说的话，但因为它能通过子串匹配而混过了证据回指校验

**修法（三处同时改）**：

| 改动 | 做法 |
| --- | --- |
| ① 拆分依据 | 新增 `splitUserExperiencePart()`，按分号句号切分，只取描述「用户经历」的那一段做判定，描述「岗位要求」的部分排除 |
| ② 补齐否定词 | DENY 增加「未说明 / 未提供 / 未体现 / 判为 / 信息不足」等表述 |
| ③ 证据必须真实 | 新增 `findRealEvidence()`，改判 have 时必须给出可回指的用户原文片段；找不到就**不改判**，记 `basis_consistency_skipped` |
| ④ 元话语拦截 | 新增 `isMetaDiscourse()`，「依据中 / 上文中 / 如前所述 / 根据要求」等一律拒绝作为证据 |

**另一个案例（T1「大模型 API 调用实践经验」判 have，证据「MySQL」）的根因链更长**：

模型把 JD 里「熟悉 MySQL 或 Redis 等常用数据库」这条要求，`ability_type` 错填成了「大模型API」→ 服务端 `canonFromType` 把 item 规范化为「大模型 API 调用实践经验」，**但 evidence 仍挂着 MySQL 那句——名实分离** → 工具技能规则看到 MySQL 就判 have → 用户看到"大模型 API 经验 = 已有，证据 MySQL"。

**修法**：

| 改动 | 做法 |
| --- | --- |
| ⑤ 名实分离防护 | 新增 `canonMatchesEvidence()`：证据撑不住规范名时，拒绝这次改名，改用证据反查能力名——**证据是 JD 原文，比模型给的名字可靠** |
| ⑥ 工具技能挂靠校验 | 工具名必须真的指向这项能力：要么出现在能力项名称里，要么该能力项的 JD 证据与能力项方向相符，否则记 `tool_skill_mismatch` 不改判 |
| ⑦ 语义相关度校验 | 新增 `isEvidenceRelevant()`：证据在原文里 ≠ 证据支撑这条能力。要求实词重叠，或证据是含动作动词的完整行为描述，或工具名确实出现在该项的 JD 描述里 |

**修复效果**：21 条 have 结论、0 条假阳性。「MySQL」那条现在正确地独立成项——「熟悉 MySQL 或 Redis 等常用数据库」，证据 MySQL，名实对应正确。

### 1.3 修复过程中额外发现的 3 个缺陷（V1.0 报告未列出）

这三个都是修 D2 时暴露的，**修一个缺陷挖出三个**：

**① JD 名实分离**：如上 ⑤ 所述。危害是让一条真实要求挂到不相干的能力名下。

**② 工具技能误挂**：原规则只检查"工具名是否出现在能力项名称或 JD 证据里"，不检查"这个工具是否真的属于这项能力"。修复后要求两者之一成立且方向相符。

**③ 竞赛判定抖动**：V2.0 复测中发现，同一份输入（用户明说"参加过学校程序设计竞赛，拿了个三等奖"），模型对「竞赛经历」项的判定在 have 与 improve 之间随机跳动——理由时而说"竞赛类型不对口"。获奖是客观事实，与类型是否对口是两件事。

修法：新增 `applyDeterministicContest()` 确定性规则，与学历/专业同样的处理思路——**客观事实由服务端兜住**。竞赛获奖 → 「竞赛经历」判 have（证据给原文），类型是否对口写在 basis 里供用户判断。

### 1.4 顺带解决的三个缺陷（未单独改代码）

**D3（信息不足占比过高）、D4（任务拆碎）、D5（翻资料型元任务）**在 V2.0 中全部消失，但**没有为它们单独写一行代码**——它们的根因都在 D1：

- D3 消失，因为 improve 出现后，"有线索但不够"不再被塞进 unknown。T4 的 unknown 从 8 条降到 2 条
- D4 消失，因为任务来源从"回忆核对"（同一件事的 8 种切法）变成"具体提升动作"（每条对应一个不同的能力项）
- D5 消失，因为计划不再是"去翻资料确认你做过没有"，而是"做一份竞品分析 / 画一份原型 / 建一张台账"

**这是本次修复最有价值的部分**：一个根因修正，三类用户可感知的体验问题同时消失。**如果不修 D1 而单独去修 D3/D4/D5，就等于在症状层面打补丁。**

## 三、剩余问题

### 3.1 D7｜差距项无对应任务（4 次命中，medium）

**现象**：T2 有 6 项、T3 有 4 项、T5 有 4 项差距没有对应任务。用户看完第 05 页的差距清单，到第 06 页找不到对应动作。

**为什么这轮没修**：D7 的根因是**不可行动项混进了差距列表**（「相关专业背景」「学历与年级门槛」这类客观条件本就不该出现在差距页）与**可行动项被漏掉**两个问题叠加。前者是服务端过滤逻辑缺失，后者涉及计划生成的任务分配策略——**两者都不是 D1 的连带效应，需要单独设计**，硬塞进这轮会让改动范围失控。

**修复建议**（已在 V1.0 报告提出，结论不变）：
- 服务端过滤不可行动项：学历门槛、专业背景、身份类要求不进入 gap_report，也不计入 summary 统计
- 建立 gap_report 与 action_plan 的双向覆盖校验：每条 gap 项要么有对应任务，要么明确标注"本阶段不安排"并给出理由

**为什么这不影响面试**：这是一个**已定位、已有明确修复方案、但尚未实施**的缺陷。面试时讲它比讲"我全修完了"更可信——真实的产品迭代里，缺陷是分批修的。

### 3.2 D6｜P0 任务由「已有」能力生成（1 次命中，low）

T5 的 P0 任务依据是已具备的「校园活动组织经历」。根因是 PRD 的优先级规则写的是「P0 = status=improve 且 weight=3」，improve 恢复后这条规则本已自洽，但模型仍有概率退化到"按 weight 定 P0"。

**修复建议**：服务端加一条校验——若任务依据对应的差距项状态为 `have`，则该任务不应为 P0。一条校验的事，但需要确认不会误伤「已有能力也要巩固」这类合理场景。

## 四、这次修复暴露的方法论问题

这一节与产品无关，但对面试很有价值。

### 4.1 自动化测试全绿 ≠ 产品是对的

V1.0 时 225 项测试全部通过，产品却有两个 P0 缺陷。**因为测试用例是围绕"预期输入"设计的，而两个 P0 都发生在"模型输出不合预期"的路径上**——一个是我的提示词自相矛盾，一个是服务端自己造了假证据。

**这说明：测试要覆盖"模型可能犯的错"，而不只是"我想要的输出"。** V2.0 新增的 20 条用例全部是"喂一个已知会出错的输入，验证服务端拦住了"。

### 4.2 修一个缺陷会挖出三个

D2 的排查过程是：先修语义校验 → 发现假证据来自 `applyBasisConsistency` → 修它 → 发现证据填的是字符串 → 追溯到名实分离 → 修它 → 发现工具技能误挂 → 修它 → 发现竞赛判定抖动 → 修它。

**四个问题串在同一条链上，因为它们共享一个根因：服务端在"帮助模型"的时候，把不该帮的地方也帮了。**

### 4.3 修复不能只看指标变好

T1 的「逻辑思考能力」在修复后从 have 变成 improve，have 总数没变，但**判定是更准的**（V1.0 的证据"竞赛 + 刷题"确实不足以支撑"逻辑思考与问题排查"）。如果只看"have 数量没下降"就判定修复成功，会漏掉这个改进；反过来如果只看"improve 从 0 变成 12"就宣布成功，会掩盖 T4 的 unknown 从 8 降到 2 这种实质体验改善。

**必须回到用户可见的场景去看，而不是只看统计数字。**
